# URL-пагинация дверного каталога

Реализовано 19.10.2026 по утверждённому brief «MVP Door Catalog Pagination — 30 товаров на страницу».

## Область изменений

- Корень `/mezhkomnatnye-dveri`, дочерние Woo-категории и SEO-посадочные выводят по 30 товаров.
- Новости и портфолио сохраняют действующую пагинацию по 12 карточек; стеновые панели не менялись.
- Навигация: номера страниц, «Назад», «Далее», обычные HTML-ссылки. Каждая ссылка ведёт к `#catalog-products`, началу товарной сетки. Prefetch ссылок отключён.
- PHP, WordPress DB, фильтрация товаров, PDP, конфигуратор, корзина, checkout и sitemap отдельных товаров не менялись.

## Данные и совместимость

Страницы передают выбранный номер и `perPage=30` существующему `getCatalogProducts`. Сервис получает все опубликованные товары дерева Woo-категории порциями REST по 100, получает matching ID из `od/v1/door-catalog-products`, пересекает наборы и только после этого нарезает карточки. Семантика OR внутри группы / AND между группами остаётся в PHP `tax_query`.

Порядок REST `orderby=date&order=desc` сохраняется. В проверенном LocalWP WooCommerce добавляет ID вторым ключом: `date DESC, ID DESC`. Frontend не пересортировывает карточки по порядку массива matching ID. При неизменных данных границы страниц стабильны.

`CatalogResult` по-прежнему содержит `page`, `perPage`, `total`, `totalPages`, `items`, состояние фильтров и категории. Сервис и `/api/catalog` сохраняют прежние значения по умолчанию (24) и совместимую обработку страницы за диапазоном. Страницы витрины явно задают 30 и самостоятельно вызывают `notFound()`, если **запрошенный** номер больше `totalPages`; подмена номера сервисом не скрывает ошибку.

Форматы REST/BFF, GET-параметры Woo/WP и исторический REST corpus не менялись. Для этого frontend-релиза импорт или миграция БД не нужны.

## URL и SEO

`page` — положительное безопасное целое число, отдельно от `FilterState`. Отсутствие параметра означает страницу 1. Ноль, отрицательные/дробные/нечисловые значения, повторённый `page`, ведущие нули и номер за диапазоном дают 404. Пустая первая страница остаётся доступной без навигации.

| Сценарий | Canonical / robots |
| --- | --- |
| Чистая категория, страница 1 / `?page=1` | URL категории без `page`, прежние robots |
| Чистая категория, `?page=2` | Собственный URL с `?page=2`, прежние ограничения индексации категории |
| Чистая SEO-посадочная, `?page=2` | Собственный URL с `?page=2`; индексируемость зависит от прежних проверок landing и количества товаров |
| Категория с фильтрами и `page` | `noindex`, прежний preferred canonical без `page` |
| Landing с query-фильтрами и `page` | `noindex`, canonical на чистую landing без `page` |

SEO Title, Description, OG/Twitter и WordPress `noindex` сохраняются. `SITE_INDEXING_ENABLED=false` сохраняет приоритет. Sitemap не получает отдельные `?page=N`.

Переход между страницами сохраняет все распознанные значения query-фильтров, включая несколько значений одной группы. На landing её правила остаются в пути и полном FilterState, а в ссылки пагинации попадают только query-фильтры текущего URL. Поэтому чистая landing не превращается в query-вариант при переходе на страницу 2.

Изменение фильтра уже использует существующий preferred URL resolver, который строит адрес заново без `page`. Форма без JavaScript также не содержит `page` и начинает выдачу с первой страницы. Алгоритм выбора preferred URL не менялся.

## Проверки и производительность

PRE-FLIGHT подтвердил существование PHP matching в `wordpress/mu-plugins/door-seo-landing.php`, отсутствие `page` среди реальных filterKey LocalWP, полный обход Woo REST и сохранение совместимости BFF. В LocalWP проверено 7 дверей, из них 2 в категории скрытых дверей; изменение БД для тестов не выполнялось.

Прямой вызов сервиса каталога на холодном процессе до и после изменения делает 4 GET (категории, filter terms, полный Woo-набор, matching ID). Время до → после: корень 1445 → 1020 мс, скрытые двери 722 → 739 мс, фильтр цвета 990 → 854 мс. Повторные вызовы: 1–3 мс, 0 GET в обоих случаях. Это локальные замеры небольшого набора, не нагрузочный тест production; разброс времени не означает подтверждённого ускорения.

Полный SSR (первое открытие / повторное в том же процессе):

| URL | До, мс | После, мс |
| --- | --- | --- |
| `/mezhkomnatnye-dveri` | 2310 / 38 | 2365 / 41 |
| `/mezhkomnatnye-dveri/skrytye` | 664 / 41 | 480 / 36 |
| `/mezhkomnatnye-dveri/ofisnye` | 446 / 37 | 628 / 38 |

Для этой последовательности из шести открытий число реальных REST START в логах standalone равно 12 до и 12 после. Последовательность использует общий процесс и его кеши; это не три независимых холодных запуска. Число товаров на страницах осталось 7 / 2 / 7. Замеры выполнены на отдельных локальных запусках порта 3107, временные серверы остановлены после проверки.

Автоматические тесты: 0/1/30/31/60/61/131 товар, полнота REST-обхода, matching до нарезки, стабильные границы, URL с несколькими фильтрами, все три renderer/metadata-сценария, 404 вместо clamp, совместимость дефолтов сервиса, HTML-ссылки и сброс номера при изменении фильтра. Существующие тесты статей, портфолио и SEO запускаются вместе с ними:

```powershell
node --test tests/door-catalog-pagination.test.cjs tests/content-pagination.test.cjs tests/seo-metadata.test.cjs
npm run lint
npm run typecheck
npm run build
```

Проверки прошли: 49 тестов, lint, typecheck, production build и подготовка standalone. Сохраняются прежние предупреждения линтера об `<img>` / `next lint` и TLS-warning локального окружения. HTTP smoke новой сборки подтвердил 200 для всех трёх каталогов и `?page=1`, 404 для некорректных/повторённых/выходящих за диапазон номеров с User-Agent Googlebot, 200 для пустой выдачи и архивов. Для браузерного User-Agent отдельно подтверждён 404 на отсутствующей странице 2 во всех трёх каталогах. `/api/catalog?type=doors` сохранил `perPage=24`, явный `&perPage=30` возвращает 30 в метаданных. Диапазоны 31+ проверены синтетически, поскольку в LocalWP 7 дверей.

## Ограничения и ручная приёмка

Полная серверная выборка остаётся техническим долгом: при росте каталога число Woo GET равно `max(1, ceil(N / 100))` для дерева категории, плюс запросы категорий, фильтров, matching и навигации. Пагинация ограничивает HTML/карточки текущей страницы, но не превращает matching в новую серверную порционную выборку. Полный набор товаров в браузер не отправляется и клиентская фильтрация не добавляется.

Кеш товаров и matching обычно 60 секунд, категорий — 300 секунд. Публикация/удаление товаров во время обхода или между переходами может менять границы страниц; единого снимка БД между HTTP-запросами нет. Производительность крупных реальных коллекций требует отдельного измерения на staging.

1. На тестовом наборе проверить 30/31, 60/61 и более 100 товаров во всех трёх сценариях. Сверить `total`, фактические карточки и отсутствие пропусков/дублей.
2. Открыть страницу 2 напрямую и после перезагрузки; проверить «Назад»/«Вперёд» браузера и возврат к началу сетки на desktop/mobile.
3. Выбрать несколько фильтров, перейти дальше и изменить фильтр: значения сохраняются при пагинации, при изменении номер сбрасывается, preferred URL пересчитывается.
4. Проверить чистую landing и landing с residual query; сверить Canonical/noindex по таблице. На публичном staging сохранить запрет индексации.
5. Проверить `?page=1`, `?page=0`, `?page=-1`, `?page=abc`, повторённый `page` и страницу за концом выдачи. При 0/1–30 товарах навигация отсутствует.
6. Без JavaScript проверить карточки, обычные ссылки пагинации и форму фильтров.
7. Проверить сохранность PDP, конфигуратора, корзины, checkout, sitemap, новостей и портфолио по 12, стеновых панелей.
8. Пройти smoke на staging до продвижения production. В рамках этой задачи staging/production deploy не выполняется.
